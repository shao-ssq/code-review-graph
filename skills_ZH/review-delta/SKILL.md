# 增量审查

仅对变更代码及其影响半径进行聚焦的、省 token 的代码审查。

**Token 优化：** 开始前，调用 `get_docs_section_tool(section_name="review-delta")` 获取优化工作流。上下文中只使用变更节点 + 2 跳邻居。

## 步骤

1. **确保图谱是最新的**，调用 `build_or_update_graph_tool()`（增量更新）。

2. **获取审查上下文**，调用 `get_review_context_tool()`。返回：
   - 变更文件（从 git diff 自动检测）
   - 受影响的节点和文件（影响半径）
   - 变更区域的源码片段
   - 审查指引（测试覆盖缺口、广影响警告、继承问题）

3. **分析影响半径**，查看上下文中的 `impacted_nodes` 和 `impacted_files`。重点关注：
   - 调用者发生变更的函数（可能需要验证签名/行为）
   - 继承发生变更的类（里氏替换问题）
   - 依赖方众多的文件（高风险变更）

4. **执行审查**，使用该上下文。对每个变更文件：
   - 审查源码片段的正确性、风格和潜在 bug
   - 检查受影响的调用者/依赖方是否需要更新
   - 使用 `query_graph_tool(pattern="tests_for", target=<函数名>)` 验证测试覆盖
   - 标记任何未测试的变更函数

5. **报告发现**，采用结构化格式：
   - **摘要**：变更的一句话概述
   - **风险级别**：低 / 中 / 高（基于影响半径）
   - **发现问题**：bug、风格问题、缺失测试
   - **影响半径**：受影响的文件/函数列表
   - **建议**：可操作的改进建议

## 相对全仓库审查的优势

- 只发送变更 + 受影响代码给模型（token 减少 5-10 倍）
- 自动识别影响半径，无需手动查找文件
- 提供结构化上下文（谁调用谁、继承链）
- 自动标记未测试的函数
